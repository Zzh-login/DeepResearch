# DeepResearch 项目面试题库

> 适用范围：Python 后端、AI 应用、RAG、Agent、全栈开发岗位。
>
> 使用方式：每题先用 30 至 60 秒讲清“结论、实现、取舍”，再根据面试官追问展开。回答中的技术事实仅对应当前项目实现，不使用没有压测依据的成功率、QPS 或准确率数据。

---

## 0. 一分钟项目介绍

**Q1：请介绍一下 DeepResearch 项目。**

**答：** DeepResearch 是我独立设计和实现的 AI 研究助手。它支持普通聊天、严格知识库问答、混合问答、自动路由和深度研究五种模式。后端使用 FastAPI 和 WebSocket 提供实时交互；知识库使用 PostgreSQL、pgvector 和 BGE-M3 做文档检索；深度研究使用 LangGraph 编排计划、本地检索、网络检索、报告生成、引用校验和自动修复；研究任务有状态机、租约、心跳、检查点、暂停恢复和异步导出机制。重点是让回答有来源边界、研究任务可恢复、模型调用可控制和用户数据可隔离。

**Q2：这个项目解决了什么问题？**

**答：** 普通聊天很难保证回答依据，长研究任务又容易因模型超时、Worker 重启或用户取消而丢失状态。项目将知识库证据、模型补充、研究来源和模型调用拆开管理：知识库问答强调证据与引用，研究任务强调可恢复执行，模型层强调超时、重试、熔断、限额和审计。

**Q3：你的个人贡献是什么？**

**答：** 我完成了架构拆分、FastAPI 路由和 WebSocket、RAG/Hybrid/深度研究图、PostgreSQL 仓储、研究任务可靠性、模型网关、长期记忆、报告导出、前端会话交互、测试和 Windows 一键启动脚本。项目当前没有依赖外部团队成员交付的核心模块。

**Q4：项目最有挑战的部分是什么？**

**答：** 三部分：第一，引用边界和提示词污染防护，不能让模型把无依据内容伪装成知识库结论；第二，深度研究是长任务，需要保证暂停、取消、失败重试和 Worker 重启后都不出现状态错乱；第三，统一模型调用，既要兼顾 DeepSeek、BGE-M3 等能力，又要记录用量、控制超时并避免故障扩散。

**Q5：为什么不直接调用大模型 API，而要做完整系统？**

**答：** 直接调用只能完成单次生成。真实应用还需要身份认证、会话管理、资料上传、检索、引用、异步任务、失败处理、成本控制和可追溯性。这个项目主要展示的是把模型能力变成稳定产品能力的工程实现。

## 1. 架构与分层

**Q6：整体架构是怎样的？**

**答：** 接入层是 FastAPI HTTP 路由和 WebSocket；应用层包括聊天编排、RAG 图、混合问答图、深度研究图和 Worker；领域层定义聊天模式、研究状态机、报告 Schema、引用和模型调用契约；基础设施层实现 PostgreSQL、pgvector、DeepSeek、BGE-M3、ASR、TTS、文件解析和网页抓取。PostgreSQL 持久化会话、知识库、研究任务、事件、检查点、导出任务、用量和审计数据。

**Q7：为什么要按 app/domain/infrastructure/interfaces 分层？**

**答：** 这样能把业务规则和技术实现隔开。比如研究状态迁移放在 `domain/research/models.py`，而 SQL 放在 `infrastructure/research/pg_repository.py`；以后替换数据库、模型供应商或 Web 框架时，对业务规则的影响更小，也更容易单测。

**Q8：`app/composition.py` 的作用是什么？**

**答：** 它是组合根，集中创建共享的 `ModelGateway` 等服务并注入应用对象。这样避免每个业务类自行构造依赖，保证生产调用经过统一的限额、熔断和审计逻辑。

**Q9：为什么仓储层不自己创建数据库连接池？**

**答：** 连接池属于应用生命周期资源，必须由 `PostgresDatabase` 统一管理。仓储只接收共享数据库对象，避免隐藏连接、重复建池、难以关闭和事务无法跨仓储协作的问题；项目中也为此写了对应测试。

**Q10：同步接口和异步接口如何划分？**

**答：** 普通聊天使用 WebSocket 流式返回；知识库上传、会话操作等使用 HTTP；耗时的研究任务和报告导出走创建任务后异步 Worker 执行，前端通过轮询或事件刷新状态。这样不会把长时间模型调用阻塞在一个 HTTP 请求中。

**Q11：为什么深度研究不放在聊天 WebSocket 里直接执行？**

**答：** 深度研究包含多次模型调用、网络请求和文件导出，时间不可控。放在 WebSocket 中会受到断连、进程重启和超时影响。采用持久化任务 + Worker 后，客户端断开不影响任务，用户可刷新页面后继续查看、暂停、恢复或下载报告。

**Q12：项目当前是多 Agent 吗？**

**答：** 严格来说不是对等协作式 Multi-Agent。当前是一个由 `DeepResearchGraph` 统一编排的多阶段 Agent 工作流，节点包括计划、本地检索、网络检索、写作、校验和修复，共享同一个研究状态。简历中应写“基于 LangGraph 的多阶段 Agent 工作流”，不应夸大为多个独立 Agent 协同系统。

**Q13：如果要升级为真正的 Multi-Agent，怎么做？**

**答：** 增加 Supervisor 负责分解和调度，并将规划、知识库检索、网络检索、阅读、写作、批评拆成有独立角色提示词、输入输出 Schema 和失败策略的 Agent；它们通过受限消息协议和共享黑板状态通信。会先以实验开关并行新旧流程，再比较质量、耗时和失败率，避免直接替换已稳定的工作流。

## 2. 聊天模式、路由与 WebSocket

**Q14：五种聊天模式分别是什么？**

**答：** `normal` 是普通聊天；`knowledge` 是严格知识库问答；`hybrid` 是知识库结论加明确标识的模型补充；`auto` 由路由器在普通、知识库和混合模式间选择；`deep_research` 创建异步研究任务。

**Q15：自动路由如何工作？**

**答：** `AutoChatRouter` 先按规则识别明显场景，再必要时用模型返回结构化路由结果和置信度。编排器会把最终模式、来源、置信度和原因带入响应元数据。手动指定模式不会经过自动路由，避免用户主动选择被覆盖。

**Q16：自动路由模型不可用怎么办？**

**答：** 采用安全降级策略：没有足够置信度或路由服务异常时，不假设有知识库证据，回退到普通聊天或提示用户选择模式。不会把不确定的内容冒充成知识库答案。

**Q17：WebSocket 为什么适合聊天？**

**答：** 可以在同一长连接上逐 token 推送模型输出，实现打字机效果，减少轮询开销。项目将 token、完成、错误等封装为事件；完成事件携带最终文本、模式和引用。

**Q18：WebSocket 如何鉴权？**

**答：** 浏览器握手时自动携带登录 Cookie 中的 JWT，服务端解码并得到 `user_id`。未认证连接会关闭，后续所有会话、知识库和研究任务查询都带 owner 条件。

**Q19：断开 WebSocket 后会发生什么？**

**答：** 普通聊天流式输出会停止；深度研究不依赖该连接，因为它已经入库并由 Worker 执行。用户重新打开或刷新页面后，可以通过会话和任务接口重新查看研究状态。

**Q20：为什么要区分 `requested_mode` 和 `resolved_mode`？**

**答：** `requested_mode` 记录用户选择，例如 `auto`；`resolved_mode` 记录实际执行结果，例如 `knowledge`。这让历史记录、审计、前端展示和问题定位都能知道用户意图与系统决策是否一致。

## 3. RAG 知识库

**Q21：RAG 的完整链路是什么？**

**答：** 用户上传 TXT、MD、PDF 或 DOCX；解析器提取文本和章节信息；分块器按大小和重叠生成 chunk；BGE-M3 生成向量；向量和元数据写入 PostgreSQL + pgvector；提问时对问题向量化，按知识库和 owner 过滤并进行相似度检索；将选中的证据构造成上下文，模型生成回答后进行引用校验。

**Q22：为什么使用 PostgreSQL + pgvector，而不是单独的向量数据库？**

**答：** 当前规模下，pgvector 可以把业务数据、权限、事务、元数据过滤和向量检索放在同一数据库中，运维成本更低。知识库删除、用户隔离和文档状态更新可以利用外键与事务一致处理。大规模高并发场景可以再评估专用向量数据库。

**Q23：为什么选择 BGE-M3？**

**答：** 它支持多语言语义检索，适合中文知识库；项目以本地模型方式加载，避免每次检索依赖外部 embedding API，也减少数据外发。代价是模型缓存较大、首次加载时间较长，需要预热和本地部署准备。

**Q24：文本分块为什么需要 overlap？**

**答：** 如果一个语义关系跨越分块边界，完全切断会降低召回质量。少量重叠能保留上下文连续性；但 overlap 过大增加存储、向量化成本和重复证据。当前通过固定 chunk 大小和 overlap，并保留章节、页码等元数据。

**Q25：Markdown 解析如何避免代码块里的标题误分段？**

**答：** 解析器会识别围栏代码块状态，仅在非代码块中把 Markdown heading 当作章节边界。项目为代码块标题、无正文标题和列表原子性写了测试。

**Q26：检索时如何隔离不同用户和知识库？**

**答：** 先根据当前 user_id 查询知识库归属，再以 `knowledge_base_id` 和 owner 为过滤条件检索 chunk。路由层、仓储层和数据模型都做 owner 约束，不能只依赖前端传来的知识库 ID。

**Q27：低相关度检索结果如何处理？**

**答：** RAG 图会检查检索数量和最小分数。没有足够上下文时进入 `no_context` 分支，不调用模型凭空回答，而是返回“根据当前知识库资料无法确定”这一类受控结果。

**Q28：为什么“无法确定”时不能展示无关引用？**

**答：** 无关引用会让用户误以为答案由这些文档支持，反而降低可信度。正确做法是无上下文时不引用，或只说明没有匹配证据；如果系统展示检索诊断，也要与答案证据区分。

**Q29：RAG 中如何防止截断后引用错误？**

**答：** 上下文截断和引用候选必须使用同一批最终纳入 prompt 的 source。不能先从完整列表生成引用，再在 prompt 中截断，否则模型可能引用未见过的证据。项目有对应的上下文与引用一致性测试。

**Q30：为什么 RAG 仍然可能幻觉？如何降低？**

**答：** 模型可能对证据过度推断、错误归因或编造引用。项目通过最小分数阈值、受限来源编号、引用解析和白名单校验、一次修复、二次失败拒答来降低风险。但这不是事实正确性的数学保证，仍需展示来源和不确定性。

## 4. 严格知识库问答与混合问答

**Q31：严格知识库问答和混合问答的区别？**

**答：** 严格知识库问答只基于检索证据回答，缺证据就拒答；混合问答允许模型补充通用解释，但必须把“知识库结论”和“模型补充”分区呈现，模型补充不能带知识库引用。

**Q32：为什么要做混合模式？**

**答：** 纯知识库模式可靠但回答范围受资料限制；普通聊天灵活但不能证明依据。混合模式兼顾两者，但核心前提是边界清晰，不能让用户误把模型常识当成库内事实。

**Q33：混合回答的结构校验有哪些？**

**答：** 校验是否包含所需分区、知识库段是否有有效引用、模型补充是否按约定标识、模型补充是否含有引用、引用是否存在于本次检索 source 集合等。校验失败会触发一次修复，仍失败则返回受控失败结果。

**Q34：为什么模型补充不能引用 `[S1]` 这类编号？**

**答：** `[S1]` 表示当前知识库的真实证据编号。如果模型补充也使用它，用户无法判断句子是否真的来自文档。因此模型补充必须以固定前缀标识，且不能声明知识库支持。

**Q35：如何防御知识库提示词污染？**

**答：** 将上传文档视为不可信数据，不把文档内容当成系统指令；提示词明确要求忽略来源中的命令或角色设定；严格模式只围绕用户问题和检索证据作答；关键边界通过测试验证，例如文档里要求“记住紫色”不能影响系统记忆或绕过回答约束。

**Q36：引用有效性校验能否证明回答一定正确？**

**答：** 不能。它证明的是引用格式存在且指向当前允许来源，减少伪引用；并不自动完成细粒度事实蕴含判断。更高要求可增加 claim-evidence entailment 模型、人工抽检和基准集评估。

## 5. LangGraph 与 Agent 工作流

**Q37：为什么选 LangGraph？**

**答：** 研究任务不是线性函数调用，而是有状态、条件分支和循环，例如校验失败后修复再校验。LangGraph 用显式节点、边和共享状态表达流程，比在一个大函数里写大量 if/else 更可读、更容易测试和恢复。

**Q38：DeepResearchGraph 的节点有哪些？**

**答：** 当前核心节点是 `plan`、`local`、`web`、`write`、`validate`、`repair` 和 `reject`。流程是生成计划，检索本地知识库和网页来源，生成结构化报告，校验引用；通过则结束，不通过时进入修复并再次校验，超过限制则拒绝。

**Q39：研究图的共享状态里有什么？**

**答：** 包括任务 ID、用户 ID、问题、知识库 ID、研究范围、计划查询、已收集来源、报告草稿、修复次数、仓储依赖、会话上下文和经过模式过滤的长期记忆。这些状态支持检查点持久化和恢复。

**Q40：研究计划为什么要求 JSON？**

**答：** JSON 可以被 Pydantic 或显式解析器验证并结构化存储为范围和子查询，后续检索节点不用从自然语言猜计划。解析失败会报出明确错误，不把格式错误的模型输出继续传给下游。

**Q41：为什么本地检索和网页检索都要保留？**

**答：** 本地知识库适合私有、可控和已有资料；网页检索补充新信息和缺失覆盖面。报告中来源类型不同，引用也需要保留来源、URL 或文档元数据，让结论可追溯。

**Q42：网页检索如何防 SSRF？**

**答：** `ResearchWebGateway` 只接受 HTTP/HTTPS，拒绝 URL 凭据、私网地址、metadata 地址和非标准端口；下载时限制重定向、响应 MIME 类型和最大字节数。这防止研究任务被诱导访问内网服务或读取异常大文件。

**Q43：研究图中为什么有 repair 回路？**

**答：** LLM 有时会输出不合法 JSON、无效 citation ID 或缺少必需引用。一次结构化修复通常能处理格式性问题；但必须限制最大次数，避免无限循环、成本失控或反复产生低质量结果。

**Q44：为什么不能让模型自己判断报告是否合格？**

**答：** 模型自评不稳定，也可能为了通过而忽略问题。项目把可确定的规则写成程序校验：必填 section、block 类型、证据引用、引用白名单、综合块的依据关系等。模型只负责生成或修复，程序负责规则执法。

**Q45：结构化报告 Schema 的价值是什么？**

**答：** 报告由 section 和 block 组成，block 区分 evidence、comparison、synthesis、limitation、recommendation 和 table。这样可以规定哪些块必须引用、哪些综合块必须指向证据块，再统一渲染 Markdown、DOCX 和 PDF，而不是从松散 Markdown 反向解析。

**Q46：为什么 `verifying -> writing` 必须合法？**

**答：** 当报告校验不通过时，需要从校验阶段退回写作阶段修复，再重新校验。因此状态机必须显式允许这一回路；如果只允许单向流转，修复会抛出非法状态迁移错误。项目有该回路的单测。

## 6. 研究任务状态机与可靠性

**Q47：研究任务有哪些状态？**

**答：** 当前状态包括 `created`、`planning`、`searching`、`reading`、`verifying`、`writing`、`paused`、`completed`、`failed` 和 `cancelled`。前六个是非终态，后三个是终态或暂停态，具体转换由领域层 `ALLOWED_TRANSITIONS` 统一限制。

**Q48：为什么要用状态机，而不是一个 status 字符串随便更新？**

**答：** 状态机使所有合法路径显式化，防止完成后的任务又被写入、取消任务被完成覆盖，或者校验失败不能回写。状态转换可以单测，数据库更新也能带前置状态条件，降低并发下的状态错乱。

**Q49：暂停是如何生效的？什么是安全边界？**

**答：** 暂停不是立即杀死正在执行的模型请求，而是写入 `pause_requested_at`。图在计划、检索、写作、校验等节点完成后的安全边界检查请求；命中后保存最近检查点、转为 `paused` 并释放租约。安全边界指数据库状态已一致、没有半写入的时刻。

**Q50：取消为什么也要分请求和最终取消？**

**答：** 对运行中的任务，立即删除或改状态可能与 Worker 完成写入竞争。因此先标记取消请求，Worker 在边界或完成事务中优先处理取消；对于尚未执行或暂停任务，可以直接最终取消。这样避免“用户取消后任务又被 completed 覆盖”。

**Q51：什么是租约？为什么不用一个 running 标记？**

**答：** 租约由 `lease_owner` 和 `lease_expires_at` 表示 Worker 在有限时间内拥有执行权。`running` 标记在进程崩溃后会永久卡住；租约过期后其他 Worker 可以安全恢复任务。Worker 还会定期续租。

**Q52：如何原子领取任务？**

**答：** 仓储使用数据库事务和 `FOR UPDATE SKIP LOCKED` 领取一条满足条件的任务，再同步写入 lease 和状态。多个 Worker 并发时，已锁行会被跳过，避免同一个任务被双重执行。

**Q53：为什么需要 PostgreSQL advisory lock？**

**答：** 独立 Worker 入口启动时会尝试获取固定 advisory lock，防止同一部署环境误启动多个主 Worker。任务级租约处理具体任务竞争，进程级 advisory lock 防止重复调度，两者解决的层次不同。

**Q54：Worker 重启后如何恢复任务？**

**答：** Worker 启动时扫描过期租约和中断状态。对普通中断任务，清理 lease、根据检查点和状态回到可重新领取状态；若已经请求取消，则最终转为 `cancelled`，清空取消请求和 lease，并记录 `task.cancelled` 事件。

**Q55：检查点保存了什么？**

**答：** 保存可 JSON 化的研究状态快照及其 hash，包括 scope、plan、sources、report draft、节点名和 attempt。恢复时把这些数据注入图的初始状态，从最近安全数据继续，避免重复已完成的搜集工作。

**Q56：为什么检查点和阶段迁移要在同一个事务中？**

**答：** 如果先更新状态后写检查点，进程崩溃会出现“显示进入下一阶段但没有恢复数据”；反过来则可能有检查点但状态仍旧。事务让两者要么同时提交，要么都不提交。

**Q57：如何区分可重试和不可重试错误？**

**答：** 超时、暂时网络错误、数据库短暂不可用等属于可重试错误，使用指数退避和最大次数；输入校验错误、非法状态、输出格式持续不合格等属于不可重试错误，直接失败并返回安全、可理解的错误。重试前要清 lease 并设置下一次尝试时间。

**Q58：如何防止重复提交创建多个研究任务？**

**答：** 前端带 idempotency key，后端把 owner、key、请求 hash 和任务 ID 存入 `research_request_keys`。相同 key 与相同请求返回原任务；相同 key 但不同请求会返回冲突，而不是静默复用错误任务。

**Q59：任务完成为什么还要二次检查取消？**

**答：** 取消可能恰好发生在最后一个模型调用结束、数据库完成更新前。`complete_task` 的事务会检查 `cancel_requested_at` 和当前状态，优先最终取消；如果任务已经是终态 `cancelled`，返回 `state_changed` 而不是覆盖。

**Q60：研究任务的进度是精确百分比吗？**

**答：** 不是严格的工作量百分比，而是与稳定阶段对应的用户可理解进度，例如规划、检索、写作、校验。它用于反馈流程状态，不能被描述为模型 token 或全部任务的精确完成比例。

## 7. 模型网关、成本与可观测性

**Q61：为什么要引入 ModelGateway？**

**答：** 如果 RAG、聊天、研究和向量化各自直接调模型，超时、重试、日志、用量和错误处理会不一致。`ModelGateway` 提供统一入口，业务代码只提供 `ModelProfile` 与 `ModelRequestContext`，网关负责供应商调用、限额、重试、熔断、用量和审计。

**Q62：ModelRequestContext 里有什么？**

**答：** 包含 owner、conversation、research task、模式、操作名称和幂等性等上下文。这样每次调用的用量和审计记录可以关联到用户与业务操作，而不是只有一条无意义的 API 日志。

**Q63：单次 Token 限额怎么做？**

**答：** 在实际调用前估算输入 token 并结合配置的输入、输出上限预留用量；超过单次限制直接拒绝。调用完成后用供应商返回的 usage 回填实际 token，缺少 usage 时标记为估算值。

**Q64：为什么只实现单次请求限额，而没有每日总额度？**

**答：** 当前目标是防止异常超长 prompt 或输出造成单次成本和延迟失控，单次限制更符合演示和开发阶段。每日配额需要用户维度的累计窗口、账务策略和管理员配置，属于后续运营能力，不应假装已上线。

**Q65：重试策略怎么设计？**

**答：** 只有标记为幂等、且错误被分类为短暂故障的调用才会重试；使用有限次数和指数退避。非幂等调用不自动重试，避免重复执行产生副作用。最终失败会记录安全错误码和审计事件。

**Q66：熔断器有什么作用？**

**答：** 同一 provider/model 连续失败到阈值后，熔断器短时间内快速拒绝请求，避免大量请求继续等待已故障服务；恢复窗口后允许探测调用，成功后关闭熔断。它保护线程、成本和用户体验。

**Q67：审计记录什么，不记录什么？**

**答：** 记录 provider、模型、操作、尝试次数、延迟、token 用量、结果码及业务关联 ID。审计层会脱敏敏感字段，并对过长非敏感内容做 hash 或不记录；不把完整用户提问、完整回答和研究报告正文直接写进审计表。

**Q68：如何定位“模型慢”还是“检索慢”？**

**答：** 模型网关记录模型调用延迟，研究任务事件记录阶段变更和检查点，数据库可查询每个 task 的 sources、usage、events；结合 Web 日志可以划分时间在向量化、数据库检索、网页抓取、模型生成还是导出。下一步可补 Prometheus 指标和分布式 trace。

## 8. 记忆、会话与用户隔离

**Q69：项目有哪些记忆？**

**答：** 有会话历史、用户长期记忆、向量记忆和归档记忆。会话历史用于当前对话上下文；长期记忆保存稳定偏好、目标或约束；向量记忆用于语义召回；归档记忆将被淘汰的旧对话压缩为摘要。

**Q70：为什么长期记忆不是每轮所有内容都写入？**

**答：** 长期记忆应保存稳定且可复用的信息，例如偏好、目标、长期约束。每轮都写会把临时问题、错误回答和噪声固化，降低召回质量并带来隐私风险。普通成功对话可以进入候选提取流程，但由提取规则决定是否持久化为事实。

**Q71：不同模式为什么需要记忆隔离？**

**答：** 严格知识库问答的结论只能来自知识库，不能让用户历史中的“事实”污染回答；混合模式只允许受控偏好；深度研究只读取目标和约束等研究相关记忆。`build_memory_policy` 和 `UnifiedMemoryService` 按模式渲染不同上下文。

**Q72：会话如何保证用户 A 看不到用户 B？**

**答：** JWT 得到 owner ID 后，所有会话读取、消息读取、知识库读取、研究任务读取和导出下载都在 SQL 层带 owner 条件。对象 ID 即使被猜到，也应得到 404 或无权限结果，而不是只依赖前端隐藏。

**Q73：会话重命名和删除如何实现？**

**答：** 会话由 PostgreSQL 的 conversations 表持久化，路由提供创建、列表、重命名、删除和消息读取接口。删除使用 owner 过滤并依赖外键级联清理关联消息、引用和关联研究内容，前端刷新后按当前会话重新加载。

**Q74：为什么刷新时会出现旧会话内容？如何解决？**

**答：** 这是前端初始化时默认会话 ID 与异步消息请求竞争造成的典型问题。解决方式是先恢复并确认 active conversation，再发消息加载请求；切换会话时递增请求版本或取消旧请求，只接受仍属于当前会话的返回结果。项目已经为研究面板的 stale response 做了相关防护测试。

## 9. 语音、文件与导出

**Q75：ASR 如何集成？**

**答：** 前端采集音频并通过 `/ws/asr` WebSocket 发送，服务端交给 SenseVoiceSmall 客户端进行本地识别，识别结果回推浏览器。模型路径可配置，默认禁止在应用启动时临时下载模型，避免生产环境因网络问题卡住。

**Q76：TTS 报 HTTP 400、超过长度限制如何处理？**

**答：** 根因是单次文本超过供应商 API 最大长度。正确处理是按句子或字符上限切分，逐段合成并按顺序播放；不能静默截断导致用户听不到后半部分。还要保留本地 TTS 或纯文本降级，并在日志中记录失败但不泄露凭据。

**Q77：为什么报告导出设计成异步任务？**

**答：** DOCX 生成和 Word 转 PDF 都可能耗时或失败，尤其是 Windows COM 自动化。异步 export job 能独立领取、失败重试、恢复中断任务和清理过期文件，不会阻塞 Web 请求。

**Q78：报告支持哪些格式？**

**答：** Markdown、DOCX 和 PDF。Markdown 适合阅读和版本管理；DOCX 适合办公协作；PDF 适合分发。报告从统一的结构化 Schema 渲染，保证核心内容与引用逻辑一致。

**Q79：为什么使用 Microsoft Word 而不是 LibreOffice 转 PDF？**

**答：** 当前 Windows 环境已经安装 Office，使用 Word 的转换能力能更接近用户本机的排版结果，减少额外安装 LibreOffice 的成本。代价是平台依赖强，不适合 Linux 容器；跨平台生产环境可改为 LibreOffice headless 或独立文档转换服务。

**Q80：下载导出物如何防路径穿越？**

**答：** 数据库只保存受控 storage key，`safe_resolve_artifact_path` 会把目标 resolve 后再验证它仍位于 artifact 根目录下；下载还要检查 owner、任务归属和过期时间，接口不向前端暴露真实存储路径。

**Q81：为什么需要导出物 TTL 清理？**

**答：** 报告文件会不断占用磁盘，且可能包含用户内容。导出 Worker 定期查找过期 artifact、删除物理文件并更新数据库状态，既控制存储成本也减少长期暴露面。

## 10. 数据库、并发与事务

**Q82：主要有哪些数据表？**

**答：** 知识库侧有 knowledge_bases、knowledge_documents、knowledge_chunks 和 ingestion_tasks；会话侧有 conversations、chat_messages 和 message_citations；研究侧有 research_tasks、research_plans、research_subtasks、research_sources、research_events、research_checkpoints、research_artifacts 和 export jobs；治理侧有 model_usage_events、audit_events、service_heartbeats 等。

**Q83：pgvector 索引如何选择？**

**答：** 项目对知识 chunk 使用 HNSW 和 cosine distance，适合读多写少的语义检索。索引参数和 top-k、最小分数应根据真实语料量、召回率和延迟压测调整；当前没有虚构大规模指标。

**Q84：数据库事务在哪些地方最重要？**

**答：** 原子领取任务、检查点与阶段迁移、取消与完成竞争处理、报告导出 job 领取、删除知识库及关联资源等场景。它们都涉及多表一致性或并发竞争，不能只靠应用层顺序调用。

**Q85：如何处理数据库不可用？**

**答：** 路由层将预期的 asyncpg 连接错误映射为 503，而不是返回堆栈或误报为用户输入错误；Worker 启动时检查数据库，循环中遇短暂故障不会直接崩溃。编程错误不会被笼统吞掉，以免掩盖 bug。

**Q86：为什么研究事件有 sequence？**

**答：** 对同一任务的事件采用递增 sequence，前端和审计查询可以按序消费、增量加载和定位状态变化。比只看最终 status 更能解释任务发生了什么。

## 11. 安全与权限

**Q87：项目有哪些安全措施？**

**答：** JWT 认证、Cookie 会话校验、SQL owner 过滤、知识库与会话隔离、上传文件路径约束、网页抓取 SSRF 防护、模型审计脱敏、artifact 路径校验、数据库异常安全映射、提示词污染边界和 API Key 通过 `.env` 管理。

**Q88：JWT 存在哪里？有什么风险？**

**答：** 当前通过浏览器 Cookie 携带，便于 HTTP 和 WebSocket 自动认证。生产还应设置 Secure、HttpOnly、SameSite 属性，配合 HTTPS、CSRF 防护、过期和刷新机制；Cloudflare Quick Tunnel 只用于面试演示，不等同于生产安全部署。

**Q89：上传文件安全如何做？**

**答：** 服务端不信任文件名和前端 MIME，限制允许格式、文件大小和存储根目录，保存时生成受控路径；解析异常写入文档状态。公开部署可进一步加入病毒扫描、对象存储和异步隔离。

**Q90：为什么 `.env` 和数据库备份绝不能提交到 GitHub？**

**答：** `.env` 可能含 API Key、TTS token 和数据库密码；数据库备份可能含用户聊天、知识库、审计和个人信息。一旦公开提交，即使删除文件也可能保留在 Git 历史中，应先撤销并轮换泄露的凭据。

## 12. 测试、评测与质量

**Q91：测试覆盖了哪些内容？**

**答：** 当前有 269 个测试用例，覆盖模式路由、RAG 引用、混合回答边界、知识库处理、长期记忆隔离、会话权限、研究状态机、任务领取、取消竞争、检查点、Worker 恢复、网页抓取安全、导出、模型网关、审计和前端关键行为。

**Q92：为什么 AI 项目不能只做单元测试？**

**答：** 单元测试只能验证确定性逻辑，如状态机、权限、引用解析和 SQL 条件；模型输出有随机性，还要做评测集、真实链路测试和人工抽检。项目有 `evals/stage9_smoke.jsonl` 和运行脚本，用来验证知识库、未知问题、混合边界、普通聊天和提示词污染等场景。

**Q93：如何评估 RAG 的效果？**

**答：** 分三层：检索层看 Recall@K、MRR/NDCG 和延迟；生成层看引用正确性、答案依据性和拒答准确性；端到端看用户任务完成率。当前 smoke eval 是回归门禁，后续应扩充人工标注问题集和来源级标注。

**Q94：如何测试提示词污染？**

**答：** 上传包含“忽略此前指令”“记住某个颜色”等注入文本的文档，在严格知识库模式提问无关问题；期望系统不会把污染文本写入用户记忆，也不会把无关指令当系统要求执行。测试要覆盖上传、检索、生成和记忆写入边界。

**Q95：如何测试取消不会被完成覆盖？**

**答：** 构造一个正在校验或写作的任务，设置 `cancel_requested_at`，再模拟 `complete_task` 执行；期望最终状态为 `cancelled`，lease 清空且产生取消事件。项目同时有单元测试和真实数据库验收脚本。

**Q96：如何测试 Worker 崩溃恢复？**

**答：** 创建领取中的任务并模拟过期 lease，保存检查点后停止 Worker，再启动 Worker；检查任务被恢复为可继续处理、lease 被清理、不会重复创建已存在的计划或来源。对已请求取消的过期任务，验证恢复结果是 `cancelled`。

**Q97：前端最重要的回归点是什么？**

**答：** 会话切换不串消息、刷新不加载旧会话、模式选择与 knowledge base 选择一致、研究任务不阻塞普通聊天、轮询在终态停止、切换会话后旧请求不覆盖新页面、导出和下载按钮防重复点击。

## 13. 部署、运维与工程化

**Q98：项目如何本地部署？**

**答：** 创建 venv 并安装 requirements；复制 `.env.example` 到 `.env` 并配置 DeepSeek 和 PostgreSQL；使用 Docker Compose 启动 pgvector PostgreSQL；按 migrations 顺序初始化新库；分别运行 Web 和 Research Worker，或使用 `start_robot_system.bat` 打开 Web、Worker 和可选 Cloudflare 窗口。

**Q99：为什么 BGE-M3 设置离线缓存？**

**答：** 运行入口在导入 transformers/huggingface 相关库前设置 `HF_HOME`、`HF_HUB_OFFLINE` 和 `TRANSFORMERS_OFFLINE`，确保模型从本地缓存加载，不会因首次检索时访问 Hugging Face 导致超时或版本不确定。

**Q100：Cloudflare Tunnel 的定位是什么？**

**答：** 它用于临时公网演示，让面试官用外部设备访问本机 Web 服务。Quick Tunnel 地址是临时的，延迟比本地访问高，不适合生产。生产应使用固定域名、HTTPS、反向代理、访问控制、日志和监控。

**Q101：为什么 Cloudflare 公网访问延迟更高？**

**答：** 请求路径变成设备到 Cloudflare 边缘、再经 Tunnel 回到本机，增加 DNS、TLS、边缘路由和公网往返时间；模型调用本身还要访问云端。用 `curl -w` 分别测本地和公网的 DNS、connect、TLS、TTFB、total 可以定位主要耗时。

**Q102：当前一键启动脚本做了什么？**

**答：** 检查 Docker 和 PostgreSQL 容器，确认端口后启动独立 Web 窗口、Research Worker 窗口，并按用户选择启动 Cloudflare Tunnel。独立窗口保留日志，便于查看登录、接口、WebSocket、ASR、RAG 和 Worker 输出。

**Q103：为什么启动器出现端口占用不能直接杀掉任何进程？**

**答：** 端口可能被另一套服务占用。安全做法是检查 PID 与可执行文件路径，只重启明确属于本项目虚拟环境的旧 Web 进程；其他进程应提示用户处理，避免误杀数据库、IDE 或别的项目。

## 14. 设计取舍与不足

**Q104：项目最大的不足是什么？**

**答：** 当前没有真正的 Multi-Agent 协作；评测集规模仍较小，缺少公开基准和长期线上指标；本地 JSON 记忆与 PostgreSQL 记忆处于兼容状态，尚未完全统一；PDF 依赖 Windows Word；Cloudflare Quick Tunnel 仅适合演示。面试中我会主动说明这些边界。

**Q105：为什么不一开始就做 Multi-Agent？**

**答：** 先完成可靠的单一编排器多阶段工作流更重要。多 Agent 会引入角色通信、任务竞争、上下文同步、成本和可观测性复杂度。现有状态机、检查点、模型网关和引用 Schema 是未来升级的基础，但不能为了概念而牺牲稳定性。

**Q106：如果数据量增长到百万级 chunk，如何扩展？**

**答：** 先测 pgvector HNSW 的召回和延迟，增加按租户/知识库的过滤索引和分区；使用混合检索、rerank 和缓存；必要时把向量检索迁移到专用向量数据库，同时保留 PostgreSQL 作为权限和元数据源。还要做批量 embedding、异步 ingestion 和队列限流。

**Q107：如果并发用户增加，如何扩展 Worker？**

**答：** 任务领取已使用行锁和租约，可启动多个 Worker 实例；需要把当前全局 advisory lock 调整为按队列或部署角色的锁策略，避免完全单实例限制。再引入任务队列、并发配额、分布式 tracing 和更细粒度的 provider 限流。

**Q108：如果要上生产，首要补什么？**

**答：** HTTPS 与 Cookie 安全属性、密钥管理、可观测性、备份和迁移策略、上传恶意文件扫描、限流、CSRF、稳定的部署方案、模型和检索评测、告警、数据保留与删除策略。还要去掉对本机 Word 和 Quick Tunnel 的依赖。

**Q109：为什么不用 Redis/Celery？**

**答：** 当前阶段使用 PostgreSQL 任务表、事务、`SKIP LOCKED`、租约和 Worker 已能满足持久化队列与恢复需求，减少一套基础设施。任务吞吐或调度需求继续增长时，可引入 Redis/Celery、RabbitMQ 或 Temporal；选择取决于优先级、延迟、可观测性和运维成本。

**Q110：为什么不直接用 LangChain Agent？**

**答：** 聊天工具循环可以用 Agent 抽象，但深度研究更需要确定的阶段顺序、显式恢复点和可验证输出。LangGraph 的图编排更适合描述流程、回路与状态；工具层仍可复用 LangChain 的消息和工具接口。

## 15. 高频追问速答

**Q111：BGE-M3 是生成模型吗？**

**答：** 不是。它在项目中用于 embedding，负责把文本转成向量以做相似度检索；回答生成由 DeepSeek 完成。

**Q112：pgvector 的 cosine 检索和 reranker 有何不同？**

**答：** 向量检索用独立编码后的相似度快速召回候选；reranker 会联合阅读 query 和候选文本重新评分，精度更高但更慢。当前项目以 BGE-M3 向量检索为主，若要提升排序质量可在 top-K 后加入本地或云端 reranker。

**Q113：为什么模型输出要限制 JSON？**

**答：** JSON 便于程序解析、验证、持久化和渲染，尤其是研究计划、报告 blocks 和路由决策。缺点是模型仍可能输出无效 JSON，因此要做 fence 清理、Pydantic 校验、修复和失败处理。

**Q114：模型调用为什么要设置 timeout？**

**答：** 防止供应商、网络或模型卡住无限占用请求和 Worker。超时后按错误类型重试或失败，并释放任务 lease；不同操作的 timeout 不同，例如研究生成比路由判断更长。

**Q115：什么叫幂等？项目哪里用到了？**

**答：** 同一请求重复执行，结果和一次执行相同。研究创建通过 idempotency key 防重复；checkpoint 按 state hash 保证重复保存返回同一记录；导出任务和完成操作也通过状态条件避免重复副作用。

**Q116：如何解释“最终一致性”在本项目中的使用？**

**答：** 研究报告完成和导出文件生成不是同一个同步事务：报告完成后创建 export job，Worker 异步生成文件，前端稍后看到可下载状态。任务和文件在短时间内可能不同步，但通过 job 状态、重试、恢复和最终 artifact 记录达到一致。

**Q117：什么是 backoff？**

**答：** 失败后不立即紧密重试，而是等待逐渐增加的时间。它降低临时故障期间的请求风暴和供应商压力；项目对可重试研究失败使用基础间隔、最大间隔和 jitter 配置。

**Q118：什么是 HNSW？**

**答：** HNSW 是近似最近邻图索引，查询速度快，适合向量检索。它以一定内存和构建成本换取低延迟；具体召回率需要通过参数和真实数据测量。

**Q119：什么是 SSRF？**

**答：** Server-Side Request Forgery，攻击者诱导服务器访问本不应访问的内网、metadata 或本地服务。研究网页抓取会验证 URL 协议、地址和端口，并限制重定向、类型和大小来防护。

**Q120：下一步你最想做什么？**

**答：** 先补评测体系：扩充有标注的检索、引用和拒答数据集，记录质量与延迟基线；然后在不破坏旧流程的前提下，用 feature flag 实现 Supervisor-Worker 多 Agent 实验流程；最后把部署改为容器化的稳定服务，并增加 metrics、trace 和告警。
